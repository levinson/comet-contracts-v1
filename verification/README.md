# Machine-checked c_pow lemmas

This Lean project machine-checks the baseline `c_pow` recurrence-error budget, geometric-tail simplification, operating-band convergence, exact-input and exact-output swap composition, successful source-shaped execution bridges for both swap directions and the exact-token-input single-sided deposit, exact-LP-amount single-sided deposit and withdrawal composition, exact-token-output single-sided withdrawal composition, proportional join and exit rounding direction, spot-price getter error and monotonicity bounds, configured limits, and application-specific signed-`I256` magnitude and denominator bounds.

The checked-in Lean constants are generated from the production Rust constants,
so the proof cannot silently keep using old pool ratios, fees, weights,
precision, exponent, or iteration limits. From the repository root, check that
the generated module is current with:

```sh
rustc --edition=2021 verification/generate_constants.rs -o /tmp/generate-cpow-constants
/tmp/generate-cpow-constants --check verification/CometCPow/GeneratedConstants.lean
```

To regenerate it after changing a source constant, replace the `--check` line
with:

```sh
/tmp/generate-cpow-constants > verification/CometCPow/GeneratedConstants.lean
```

Then run the proofs with:

```sh
cd verification
lake build
```

Elan caches the pinned Lean compiler outside the repository. To populate that persistent cache explicitly before the first build, run `elan toolchain install leanprover/lean4:v4.19.0`; later `lake` commands reuse `~/.elan/toolchains/leanprover--lean4---v4.19.0`.

The checked-in `lake-manifest.json` pins the complete dependency graph, so routine local builds should not run a bare `lake update`; that command refreshes every Git dependency and can fetch substantial Mathlib history. After intentionally changing one dependency pin in `lakefile.toml`, run `lake update <package-name>` once, commit the resulting manifest, and return to `lake build` for normal development.

The project pins Lean and mathlib to version 4.19.0. The
`c_pow formal verification` workflow first rejects a stale generated constants
module, then runs the build for every relevant pull-request change and rejects
proof sources containing `sorry`, `admit`, or custom `axiom` declarations. It
also audits the compiled `CometCPow` namespace transitively, allowing only
Lean's standard `propext`, `Classical.choice`, and `Quot.sound` foundations.

The verification project is development-only. It is not a dependency of any
Rust crate and does not alter the contract's instructions, memory use, or WASM
size.

## Minimum-fee comparison

For the below-one, round-up fractional path used by an exact-input swap, a one-term result receives the baseline's one-unit upward correction and therefore has no adverse approximation error. If the loop reaches an iteration `N >= 2`, the preceding computed term was greater than `CPOW_PRECISION`. The configured maximum input ratio and minimum fee sharpen the exact-input contraction factor to strictly less than `1/4`, so the `3k - 2` recurrence-error bound implies

```text
CPOW_PRECISION < abs(T_1) * (1/4)^(N - 2) + (3(N - 1) - 2).
```

For every `2 <= N <= 46`, Lean checks that this continuation threshold forces the complete accumulated rounding budget below `(MIN_FEE / STROOP) * abs(T_1) / 20`. At `N = 2`, where the finite table reaches its maximum fee share, the sign-specific first-term floor property proves `CPOW_PRECISION < abs(T_1)` without the generic one-unit error slack. A Taylor-remainder proof derives the generalized-binomial recurrence from the derivatives of `(1 - q)^a` and proves every finite partial sum is an upper bound on the exact below-one power, so the omitted negative tail cannot increase adverse error. Finally, `abs(T_1) = BONE * fractional_exponent * base_displacement`, while the minimum fee's spot-normalized value is `MIN_FEE_RATE * BONE * full_exponent * nominal_input_ratio`; the fractional exponent does not exceed the full exponent, and the computed base displacement does not exceed the nominal input ratio. This proves the adverse fractional approximation error is strictly below 5% of the minimum fee's continuous spot-normalized output value. The below-one integer factor is at most one and cannot amplify the comparison.

The operation-level theorems instantiate the exact-input caller's fee-adjusted input floor, normalized base ceiling, weight-ratio exponent floor, below-one integer/fractional composition, final output multiplication floor, and token downscale floor. They cover an integer exponent, the degenerate unit-base fractional result for which the implementation intentionally skips its one-unit correction, a non-unit fractional path that stops after its first term, and a fractional path that reaches a later term. In the multi-term case, the three floor refinements derive the per-step recurrence inequality, which derives the aggregate partial-sum and previous-term bounds. The iteration-46 convergence theorem is then applied to the same computed-term trace, so `N <= 46` follows from the loop continuation condition instead of appearing as an independent premise. `ExactInputSwapSource.lean` now evaluates the bounded loop and every checked outer arithmetic operation as an executable `Option` model. Its `c_pow` bridge consumes the caller's actual BONE-scaled exponent, proves that scaling preserves the integer and remainder components, and models Rust's `as u32` conversion modulo `2^32`; the configured `MIN_WEIGHT` and `MAX_WEIGHT` bounds limit the integer part to 9, making that conversion exact. A successful result supplies the trace and floor/ceiling premises automatically; in particular, its recurrence proof uses only prefixes the loop actually evaluated and does not postulate successful future iterations after an early stop.

This is a one-sided safety result, not a bound on absolute approximation error. Conservative error may exceed the stated percentage without harming the pool, particularly for very small one-term inputs. The final token-unit floors are included directionally because they can only decrease the user-visible exact-input output; the fee denominator remains the minimum fee's continuous spot-normalized value.

For exact output, Taylor's theorem proves that every odd partial of `(1 + q)^a` is an upper bound. If the approximation stops on an odd term, the baseline retains that odd partial. If it stops on an even negative term, the round-up correction removes that term and leaves the preceding odd partial. The first-term correction is conservative; at the second stop, removing the negative term leaves only the first term's sub-unit floor error; later stops use the same concrete three-floor recurrence budget and derive `N <= 46` from the loop trace.

Above-one integer powers require an additional composition argument because they can amplify fractional error. The proof derives `integer_part <= 9` from the configured weight ratio and its ceiling. Below nominal ratio `1e-5`, the rounded base is below `1.02` and its whole power is below two, so the weighted fractional term remains bounded by the full ideal exponent after accounting for the exponent-ceiling unit. At larger ratios, the whole power is below 64 and the universal `3151`-unit recurrence budget is directly smaller than 5% of the ideal minimum-fee scale. The sharpened continuation result proves `base - 1 <= 1.52 * nominal_ratio`, leaving strict margin for the exponent ceiling.

The exact-output entry theorems then compose the base and exponent ceilings, upper-rounded `c_powi`, fractional approximation, final `c_pow` ceiling, input multiplication ceiling, actual fee-denominator ceiling, and token downscale ceiling. They prove that ideal required input minus returned required input is strictly less than 5% of `MIN_FEE_RATE * input_balance * ideal_exponent * nominal_output_ratio / (1 - actual_fee_rate)`. This is the minimum fee's continuous spot-normalized input value adjusted by the same fee denominator used by the caller. `ExactOutputSwapSource.lean` evaluates that arithmetic as an executable `Option` model, derives every refinement from a successful return, and restricts recurrence premises to the prefixes the production loop actually reached.

## Additional operation paths

The exact-output fractional path has a larger base displacement than exact input. `OperationFeeBound.lean` retains the second binomial term's division by two and proves the abstract one-thirty-second first-term budget; `BinomialAboveUpper.lean` and `ExactOutputSwap.lean` now discharge its analytic direction, concrete recurrence, whole-power, and caller-composition obligations. The older `8/5` displacement bridge remains useful for abstract operation comparisons, while the complete swap theorem uses the sharper `38/25` bridge to absorb the exponent ceiling and above-one whole-power composition.

Single-sided operations charge the weighted fee `(1 - weight) * swap_fee`. For the exact-LP-input withdrawal's reciprocal exponent, Lean proves that the fractional part of `1 / weight` is at most `(1 - weight) / weight`, so the smaller fee and reciprocal exponent compensate algebraically. Its operation-level theorems cover the integer-only, unit-base, corrected first-term, and multi-term `c_pow` cases and include the supply-ratio and exponent rounding, upper-rounded whole and fractional power composition, new-token-balance ceiling, fee multiplication floor, token downscale floor, and successful maximum-output guard. In the `[0.5, 1]` operating band, the multi-term theorem derives convergence by iteration 46 rather than assuming a stop index.

The exact-LP-input caller checks `MAX_OUT_RATIO` only after `c_pow`, so the proof does not use that check as a convergence precondition. Instead, it handles a rounded remaining-supply base below `0.5` independently of the approximation: the ideal withdrawal exceeds 45% of the output-token balance after the worst configured fee, whereas a successful caller returns at most the roughly one-third maximum-output ratio. The low-base result is therefore strictly pool-favoring. Combining that result with the in-band recurrence theorem removes the public entrypoint's former `computed_base >= 0.5` restriction.

For the exact-LP-output deposit, both the direct supply base and reciprocal exponent are rounded upward. Lean proves that a continued approximation makes the nominal mint ratio large enough to absorb both ceiling units, bounds the rounded displacement by `1.01 * nominal_ratio`, and bounds the reciprocal fractional part by `1.001 * (1 - weight) / weight`. Retaining a one-twenty-fifth first-term recurrence budget leaves sufficient margin for the smaller weighted fee throughout the full `[1, 1.6]` operating band. The later theorem derives `N <= 46`; the operation-level theorems then compose every `c_pow` control-flow case with the new-token-balance ceiling, weighted-fee division ceiling, and final token downscale ceiling.

The exact-LP-output caller enforces `MAX_IN_RATIO` only after `c_pow`, so the proof does not treat that check as a precondition. Instead, it first proves a coarse lower bound across the entire accepted above-one `c_pow` base domain: through the 50-iteration cap, the retained odd fractional partial exceeds `BONE - 3725`, the upper-rounded whole power is at least the base because the reciprocal exponent has a positive integer part, and the final ceiling preserves their product. Any rounded base above `1.6` would consequently require more than half of the input balance before the fee while the successful caller permits less than half. Thus the post-calculation guard implies `computed_base <= 1.6`, after which the sharper convergence and fee-relative bounds apply. The integer-only and corrected-first-term cases remain pool-favoring without this argument.

For direct weight exponents, the exact second term contains the same `(1 - weight)` factor as the fee; retaining that factor proves the later-iteration adverse error is below 5% across the full operating band. For the exact-token-output withdrawal, Lean additionally proves that all non-constant below-one terms are negative and that the entire omitted tail is at most the magnitude of the last retained term when the rounded base is at least `0.5`. Consequently, the baseline's doubled final negative term is a true lower bound after second and later stops. The one-unit first-stop correction is also conservative. The operation-level theorems compose those results with the before-fee ceiling, base floor, new-supply floor, and final LP-token ceiling; favorable fee-division and base-floor displacement absorbs the difference between the computed-base fee scale and the exact adjusted minimum-fee scale. The later in-band theorem derives `N <= 46` from the concrete recurrence trace.

The exact-token-output caller checks its maximum token-output ratio before `c_pow`, so the production output, weight, and fee limits bound the exact adjusted ratio by `3/8`. A pathologically small native-unit balance can nevertheless make the indivisible before-fee ceiling push the rounded computed base below `0.5`. Lean handles that region separately: the favorable gap between the exact and rounded bases is larger than the exact tail after the first term, and the concrete three-floor recurrence preserves non-positivity of every later computed term. The computed power is therefore below the exact adjusted power, making the complete LP-token result pool-favoring without requiring a low-band convergence theorem. The actual 50-iteration loop cap is an explicit trace premise in that case.

For the exact-token-input deposit, the public caller checks `MAX_IN_RATIO` before invoking `c_pow`. The fee-adjusted input floor and balance-ratio floor therefore place every computed base in `[1, 1.6]`, and the direct normalized-weight exponent lies strictly between zero and one, so no integer-power factor can amplify fractional error. Lean proves the unit-base and zero-first-term results conservative, bounds the corrected first-term result's adverse omitted tail below 5% of the weighted minimum fee, proves the second-term result pool-favoring from the signs of its three floors, and handles every later odd/even stop through an even generalized-binomial lower partial. The later theorem derives `N <= 46` from the concrete recurrence trace.

Ordinary proportional `join_pool` and `exit_pool` do not call `c_pow` and do not charge a swap fee. Their relevant property is instead zero adverse rounding direction. The operation-level Lean theorems model the common LP-token upscale, each token balance's decimal upscale, the normalized ratio ceiling or floor, the token multiplication ceiling or floor, and the final token-unit downscale. Per token in the caller loop, a join therefore cannot charge less than the ideal proportional deposit and an exit cannot pay more than the ideal proportional withdrawal.

The two public spot-price getters share the same three-floor balance-per-weight and ratio calculation; the fee-adjusted getter applies one additional floor. For active token records with at least one native balance unit, positive weights no larger than `STROOP`, and a fee below `STROOP`, Lean derives positivity of every divisor. If `D` is the positive floored output balance-per-weight value, the normalized result is strictly below `ideal + ideal / D`. Only the output-denominator floor can raise the result above the continuous ideal. In the other direction, the normalized result is strictly above the ideal less `STROOP / (exact_output_balance_per_weight * (STROOP - fee)) + 1 / (STROOP - fee) + 1 / STROOP`, accounting for the numerator, ratio, and final floors. The zero-fee final calculation returns the integer ratio unchanged; the fee-adjusted getter cannot return less than the zero-fee getter and is monotone in the fee. The same floor-refinement argument proves that the balance update performed by either swap cannot decrease its computed post-swap spot price. `SpotPriceSource.lean` defines an executable `Option` model of the successful positive-denominator sequence of `fixed_div_floor(...).unwrap_optimized()` calls in `calc_spot_price`. From the model's final `some price` result, Lean recovers the intermediate source-shaped trace automatically, uses the pinned companion i128 execution proof to derive every rounding premise, and applies the complete error theorem directly to `price`; no rounding or trace premise is exposed at this theorem boundary.

A fully exited pool can have zero token balances and therefore has no defined spot-price divisor. The active-record premise is necessary rather than merely a proof convenience; getter behavior for an empty pool remains part of the contract-level API design rather than this arithmetic result.

## Fixed-point implementation refinement

The reusable checked-`I256` and checked-`i128` models are maintained on the companion `proof/formalize-i256-fixed-point` branch of `soroban-fixed-point-math`, pinned here to proof commit [`2867a65`](https://github.com/blnt-protocol/soroban-fixed-point-math/commit/2867a65e1c999f9a4242500e58aca0be22c32afa). They prove that the positive-denominator `I256` algorithms and non-widening `FixedPoint for i128` algorithms in `src/i256.rs` and `src/i128.rs` refine mathematical floor and ceiling under explicit checked-arithmetic hypotheses. That proof commit is based on `script3` upstream commit `c85960e`; its Rust source is byte-for-byte identical to the implementation shipped by the exact `soroban-fixed-point-math` 1.5.0 dependency pinned here. This project retains only the application-specific premises and operation-level compositions.

All production fixed-point denominators in `c_pow` are positive. Negative-denominator behavior is therefore outside the proof composition required by this contract.

## Assurance boundary

For `swap_exact_amount_in`, `swap_exact_amount_out`, `dep_tokn_amt_in_get_lp_tokns_out`, `wdr_tokn_amt_in_get_lp_tokns_out`, `wdr_tokn_amt_out_get_lp_tokns_in`, and `dep_lp_tokn_amt_out_get_tokn_in`, this project completes the operation-level mathematical composition for every production control-flow case reached by a successful positive-base call. These results include both generalized-binomial tail directions, the three mathematical floors in every fractional recurrence update, exponentiation-by-squaring traces for upper-rounded `c_powi`, final directional `c_pow` multiplication, directional token scaling, weighted-fee multiplication or division, final integer rounding, and the exact-LP-amount paths' post-calculation ratio guards. The exact-input swap, exact-output swap, and exact-token-input deposit source bridges construct those traces and refinements from successful executable arithmetic-model results; the other entry theorems still consume explicit loop traces and mathematical `IsFloor`/`IsCeil` refinements rather than assuming the resulting high-level error or direction bounds.

For proportional `join_pool` and `exit_pool`, the project completes the per-token operation-level mathematical composition of the production upscales, fixed-point ratio division, fixed-point token multiplication, and final token downscale. Because the public callers apply the same ratio independently to every token record, these per-token results establish the rounding direction for the full successful loop.

For `get_spot_price` and `get_spot_price_sans_fee`, the project completes the successful positive-denominator source-shaped fixed-point composition for active token records, including checked i128 representability, divisor safety, both sides of the nested-floor error envelope, the relationship between fee-adjusted and zero-fee results, fee monotonicity, and the post-swap balance-update direction.

The project does not yet provide end-to-end machine-checked source correspondence for every deployed baseline entrypoint. The exact-input swap, exact-output swap, exact-token-input deposit, and spot-price bridges now construct the checked arithmetic premises from successful executable source-shaped model results. For the exact-token-output withdrawal, both exact-LP-amount paths, and proportional join and exit paths, the remaining assurance boundary is constructing those premises from the deployed Rust control flow and mechanically composing each floor/ceiling operation with the companion fixed-point implementation-refinement theorem. As throughout the project, correspondence between the hand-written Lean models and Rust remains reviewed rather than produced by verified Rust extraction. Record/configuration reads, token transfers, authorization, event emission, and public guards other than the arithmetic invariants explicitly supplied to the entrypoint theorems are outside these arithmetic models. Primitive Soroban host operations are trusted to satisfy their protocol-specified checked-integer semantics.
